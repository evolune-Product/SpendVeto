How to put spending controls on MPP agent payments

Plug SpendVeto into the mppx client's onChallenge hook. Every offer an MPP server makes — a charge, a session deposit or a subscription — goes to SpendVeto's policy engine before mppx creates a credential. It is priced in USD or refused, checked against your budgets, approval line and payee rules, and the money it allows stays held against the budget until the payment is reported.

Plug it into mppx

MPP is the HTTP 402 payment standard Stripe and Tempo launched on March 18, 2026. A server answers 402 with one WWW-Authenticate: Payment challenge per offer, and the official client, mppx, pays one by itself. Its docs point at the onChallenge hook as the place to apply a spending policy before paying — that is where SpendVeto goes:

import { Mppx, tempo } from "mppx/client";
import { governMppx } from "spendveto/integrations/mppx.js";

const governed = governMppx({ address: account.address });
const mppx = Mppx.create({
  methods: [tempo({ account })],
  onChallenge: governed.onChallenge,   // decided before a credential exists
  polyfill: false,
});
const res = await governed.fetch(mppx, "https://api.example.com/search");

A refused offer throws before mppx signs anything. An offer above your approval line waits for a human, then is decided again. governed.fetch reports how each payment ended, with the server's Payment-Receipt kept as evidence.

The policy

{
  "$schema": "https://spendveto.com/schemas/policy-v1.json",
  "maxPerCallUSD": 0.50,
  "maxPerHourUSD": 5,
  "requireApprovalAboveUSD": 1,
  "allowedChains": ["tempo", "base"],
  "allowedPayees": ["0xVendorA…"],
  "mpp": {
    "maxSessionDepositUSD": 2,
    "maxUnitPriceUSD": 0.001,
    "allowedMethods": ["tempo", "stripe"]
  }
}

What each MPP intent is decided on

IntentDecided onAlso enforced
chargeThe amount, in USDEvery splits recipient must pass the payee rules too — a split can't route money to an address the policy never approved.
sessionThe deposit it locks — not the per-unit priceCapped by mpp.maxSessionDepositUSD; the escrow must be Tempo's channel reserve; the deposit is held until the session closes; vouchers are cumulative and can't exceed the approved deposit.
subscriptionThe first periodAlways a human approval, shown with the total until the subscription ends; a Tempo offer billing monthly is refused.

What the client library lets through

mppx parses some challenges the protocol says a client must not pay. SpendVeto refuses them before signing:

  • A challenge that has already expired.
  • A challenge asking for the credential in a header other than Authorization or Payment-Authorization.
  • A Tempo offer with no chainId — the method drafts disagree on the default (testnet for charges, mainnet for sessions).
  • A token or payment method SpendVeto can't price. Nothing is assumed to be worth a dollar.

Why the budget still sees MPP money

SpendVeto isn't in an MPP payment's path — mppx pays the server directly. So everything it allows is held against the same hourly budget as your x402 payments, cards, payouts and model tokens until the outcome is reported. An allowed charge nobody reports is booked as paid when its challenge expires: unreported spend never disappears from the budget.

MPP and x402

Both answer an HTTP 402. x402 settles each request on its own; MPP adds sessions (one deposit, many metered calls) and subscriptions, and its docs note that x402's exact scheme maps onto MPP's charge. SpendVeto governs both with one policy — see x402 spending limits.

Questions

Does SpendVeto replace mppx?

No. mppx still creates the credential and pays the server. SpendVeto decides first, inside mppx's own onChallenge hook, and books the outcome from the server's Payment-Receipt.

Which MPP payment methods are priced?

Tempo (OUSD, pathUSD and USDC.e on mainnet and the Moderato testnet), EVM (the chain's registered USDC), and Stripe and card offers in USD. Any other method or token is refused rather than guessed.

How is a session's spend counted?

The whole deposit is held against the hourly budget while the session is open. Vouchers are cumulative and can't exceed the approved deposit; closing the session books what was consumed and releases the rest.
