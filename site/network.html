The trust layer between AI agents and the businesses they pay.

Every payment platform can cap what an agent spends on its own rail. But an agent pays a model provider, an API in stablecoins, a vendor by card and a contractor by bank transfer, and none of those businesses can tell whether anyone is in control of it. SpendVeto adds three open pieces on top of its policy engine. Each one gets more useful with every other company that runs it.

1 · Spend attestations

The payment carries signed proof that the buyer's policy allowed it. Sellers verify it offline and can refuse agents nobody governs.

2 · Shared reputation

Report a scam payee once; every company that trusts you refuses it, on every rail. Feeds carry hashes, never data.

3 · An open policy standard

Agent budgets as a published JSON Schema, linted in CI so a typo can't silently remove a limit.

1 · Governed-spend attestations: 3-D Secure, for agents

When an agent is about to pay, SpendVeto runs its normal checks: budgets, approvals, payee rules, kill switch. Only if the answer is yes does it sign a five-minute token naming the payer, the payee, the resource, a USD ceiling and the policy version. Above the approval line, it signs only after a human has approved. The token rides with the payment as X-SpendVeto-Attestation. The SDK, the MCP server and the proxy attach it automatically.

The seller pins the buyer's issuer address (published at /.well-known/spendveto-issuer.json) and checks one secp256k1 signature. It makes no call to SpendVeto and shares no data:

import { requireGovernedAgent } from "spendveto/integrations/seller-express.js";

app.get("/api/report",
  requireGovernedAgent({ trustedIssuers: ["0xBuyerIssuer…"], audience: "0xYourPayTo…", price: 0.25 }),
  (req, res) => res.json(report(req.spendveto))   // verified claims: payer, ceiling, policy version
);

It refuses a missing token, a forged or self-minted one, one issued for another payee, price, resource or payer, an expired one, and a replayed one. Each refusal comes with a code naming the root cause, and the middleware won't start without a trust list. The seller learns that a policy governed the spend and which version. It never sees the buyer's limits, because a seller who could read a budget could price to it.

What an attestation proves, and what it doesn't. It proves the named issuer's engine said yes to this payer, payee, resource and ceiling at that time. It doesn't prove the payment happened (that's the rail's job), or that the issuer's policy is strict. Whether an issuer is good enough is the seller's judgment about that issuer.

2 · Shared counterparty reputation: one report protects every subscriber

The payee that just drained one company's agent is, by definition, new to the next one. A local blocklist can't help with that. With SpendVeto:

  1. Report a counterparty as block or review: a crypto address, a UPI VPA, an IBAN, an email, a domain, or a card network merchant id. From that moment the policy engine, payouts and card authorizations refuse it, or hand it to a human, whichever rail the money would use.
  2. Publish your reports as a signed feed of hashes. Raw identifiers, free-text reasons, amounts and customers never leave your instance.
  3. Another company imports your feed only if it explicitly trusts your issuer address. A feed edited after signing breaks its digest. An older feed can't be replayed over a newer one, so when you withdraw a report it stays withdrawn.

Each subscriber decides what an imported report does: refuse outright, or send it to a human. Canonicalization makes one counterparty one hash, so checksum casing, a URL versus its bare domain, and a spaced IBAN all match. Case-sensitive addresses keep their case.

Honest limit. Hashing keeps identifiers away from a casual reader, not from someone who can guess them. An email or VPA is guessable, and anyone can hash a candidate and look it up. Publish what you'd be comfortable confirming.

3 · An open policy standard for agent budgets

A misspelled limit fails open. maxPerHourUsd isn't maxPerHourUSD, so the engine never reads it, and the agent runs on a budget nobody wrote. The SpendVeto policy file is now a published JSON Schema at spendveto.com/schemas/policy-v1.json. Point a policy file at it with "$schema" for editor autocomplete, and lint it anywhere:

spendveto validate policy.json --strict
#   error    /maxPerHourUsd  unknown key "maxPerHourUsd" — … did you mean "maxPerHourUSD"?

# .github/workflows/policy.yml — no install, nothing sent anywhere
- uses: revanthrajeev/spendveto@main
  with: { policy: config/agent-policy.json, strict: true }

The validator catches unknown keys, wrong types, unregistered chain ids, and limits that contradict each other, such as an approval threshold above the per-call cap. It implements exactly the JSON Schema keywords the schema uses and refuses a schema that uses any others, so no rule can go silently unenforced.

Why a platform can't copy a network

  • It gets better with other people's adoption. A seller can only require governed agents once buyers can prove governance, and every buyer that can makes requiring it cheaper for the next seller. Every publisher makes every subscriber's blocklist better. A rival that starts later starts with an empty network.
  • It has to be neutral. An agent's budget spans rails that compete with each other. A card network, a processor or a model provider can govern its own traffic. It can't be the referee of everyone else's.
  • The formats are open. Anyone can verify an attestation with any Ethereum library, implement a feed, or validate a policy. The specification is public and the reference implementation is Apache-2.0. Standards spread because nobody has to ask permission.
  • Your data stays yours. There is no central database to trust: issuers sign, verifiers verify, subscribers choose whom to trust.

Every behavior on this page is exercised by npm run verify (458 end-to-end assertions): offline verification, forged and replayed tokens, payer binding, feeds refused until trusted, edits and rollbacks rejected, the same report enforced on payouts and card swipes, and the GitHub Action failing a typo.

Questions

What is a governed-spend attestation?

A short-lived token, signed by the buyer's SpendVeto instance only after its policy allowed a payment, naming the payer, the payee, the resource, a USD ceiling and the policy version. It travels with the payment as an X-SpendVeto-Attestation header, and the seller verifies it offline against the issuer address it trusts.

How does a seller require governed AI agents?

Add one Express middleware, requireGovernedAgent({ trustedIssuers, audience, price }), in front of the paid route. It refuses requests with no attestation, a forged or self-minted one, one for another payee, price, resource or payer, an expired one, or a replayed one. It never calls SpendVeto and refuses to start without trusted issuers.

Does sharing reputation mean sharing customer data?

No. A reputation feed lists SHA-256 hashes of counterparty identifiers with a kind and severity — no raw addresses, reasons, amounts or customers — signed by the publisher. Hashing keeps identifiers from a casual reader, not from someone who can guess them, so publish only what you would be comfortable confirming.

Why can't a payment platform just build this?

A platform can build spend limits for its own rail. An agent's spending crosses model providers, stablecoins, cards and bank payouts, and a seller needs proof that holds whichever rail the money used. The attestation, reputation-feed and policy formats are open and get more useful with every company that runs them, which a single rail owner can't replicate by itself.
