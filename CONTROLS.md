# SpendVeto control inventory

**What this is:** every governance control SpendVeto enforces, mapped to the runtime expectations that appear in current AI-governance frameworks (EU AI Act, NIST AI RMF) and enterprise agent-deployment checklists — with, for each control, the `npm run verify` assertion that exercises it end-to-end on every change.

**What this is not:** a certification. SpendVeto has **no SOC 2, no ISO 27001, no external security audit** — pre-mainnet for every chain by default. XRPL mainnet settlement is wired but disabled unless an operator explicitly opts in, entirely at their own risk; we do not run or control anyone's deployment. This document is a self-assessment whose factual claims are machine-checked by the suite (466 assertions), nothing more. Framework references describe *which expectation a control addresses*, not conformity with the framework.

## How to read the table

- **Control** — what SpendVeto enforces, in the product's own terms.
- **Framework expectation addressed** — the runtime requirement this maps to: EU AI Act Article 12 (record-keeping / logging), Article 14 (human oversight, including the ability to intervene or interrupt); NIST AI RMF functions (GOVERN / MAP / MEASURE / MANAGE).
- **Exercised by** — a representative assertion label from `scripts/verify.mjs` (run `npm run verify` and grep the label). Many controls are covered by several assertions; one is cited for traceability.

## Known gaps (deliberate, stated plainly)

- **UPI is an evaluator, not a rail** — no UPI initiation or settlement, no PSP/PA status, no NPCI or RBI approval; NPCI's agent protocol is not live. The daily-cap tally is in-memory (process lifetime). Thresholds are the RBI framework's published defaults, to be re-verified by the operator against the RBI text.
- **The LLM guard decides on an estimate** — input sized from the request, output from its `max_tokens` (capped) — so the last request allowed under a budget can overshoot it by that one request's difference; actual cost is always booked from the provider's usage. Claude-subscription traffic is metered at API-equivalent prices (not a bill). Message Batches and other endpoints it can't meter are refused, not passed through. Prices are a dated table (2026-10-18) the operator must keep current or override.
- **Payouts record the provider's status at acceptance** — asynchronous outcomes (a RazorpayX reversal, an ACH return) aren't consumed from provider webhooks yet; `POST /api/payouts/:id/status` records one. Payout approvals live in memory like every approval here: a server restart leaves a waiting payout to expire (fails closed).
- **Card governance decides authorizations only** — captures, reversals and refunds aren't consumed yet; an approved authorization is booked as committed spend. USD only.
- **Attestations prove a decision, not a payment, and not a strict policy** — the seller learns the policy's hash, not its limits; whether an issuer's policy is good enough is the seller's judgment about that issuer. An instance without `SERVER_SIGNER_KEY` signs with a per-process key, so its issuer address changes on restart. The replay guard is in memory (per process).
- **Reputation feeds hide identifiers from casual readers, not determined ones** — anyone can hash a guessable identifier (an email, a VPA) and look it up. Feeds are exchanged by hand or by your own automation (`POST /api/reputation/import`); there is no hosted feed directory yet. On cards, a `review` verdict declines, because an authorization can't wait for a human.
- **auth-capture is the buyer's ledger, not a chain reader** — lifecycle events (capture, void, refund, reclaim) reach it from whoever observes them; it does not yet read `AuthCaptureEscrow.paymentState` onchain to confirm them, and it does not submit `reclaim` itself (that call is the buyer's wallet's).
- **No external security audit** and **no mainnet settlement** — treat as pre-audit software; don't point it at funds you can't afford to lose.
- **No SSO/SCIM, no orgs/multi-tenancy** — the admin surface is API-key + roles; enterprise identity integration belongs to the hosted milestone.
- **No data-residency controls** — storage is local JSON on your own host (which *is* the residency story for self-hosting: your infra, your region), but there is no managed regional storage.
- **No ERP integration** — the billing sink emits events; mapping them into SAP/Oracle/NetSuite is downstream work.
- **SOC 2 / ISO 27001** — not started, on purpose at this stage; this inventory is the groundwork a future audit would formalize.
